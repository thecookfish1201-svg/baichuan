# 百川 · 产品章程 v1.0

> 状态：正式产品方向  
> 适用版本：v0.4.0 起  
> 产品路线：A —— 个人 AI 对话工作台  
> 产品口号：未至彼岸，仍可同行。

---

## 1. 产品定义

**百川是一款面向多模型用户的个人 AI 对话工作台。**

它是一款本地优先、用户自主配置模型服务的 Android 客户端。用户可以在一个稳定、统一的界面中连接不同模型，管理自己的助手、人设、会话和数据，不必被某一家模型服务商或某一种聊天平台绑定。

百川不负责训练或托管大模型，也不要求项目方运营模型 API、账号体系或云端同步服务器。模型服务、API 费用和能力取决于用户选择的服务商；百川负责把连接、会话、数据和日常使用体验做好。

### 一句话定位

**把不同模型带进同一个可靠、顺手、由用户掌控的对话工作台。**

### 核心主张

- 模型可以更换，使用习惯不应被迫重来。
- 对话和配置由用户掌控，不把数据所有权交给某一家平台。
- 功能应当降低使用成本，而不是让用户学习一堆复杂开关。
- 稳定、顺手、可预期，比功能数量更重要。

## 2. 产品目标与非目标

### 2.1 当前阶段的三个产品目标

1. **统一对话入口**：不同模型使用同一套聊天界面、消息操作、输入框和反馈规则。
2. **稳定的多模型体验**：模型配置、能力差异和请求错误由百川妥善处理，而不是让用户面对供应商协议细节。
3. **个人数据可控**：会话、助手、人设、附件、记忆和备份具备清晰、可靠、可理解的管理方式。

### 2.2 明确不做什么

百川当前不是：

- 一个自研基础模型或模型托管平台；
- 一个以自主 Agent、MCP 工具调用和复杂自动化为核心的智能体平台；
- 一个必须依赖官方云端账号、云端数据库或运营服务器才能使用的服务；
- 一个追逐每家模型官方 UI、为每个模型维护一套聊天页面的皮肤集合；
- 一个功能入口很多、但大量入口处于“规划中”或点击无反应的功能展厅。

Agent 执行、MCP 工具执行、代码插件运行和工作流编排可以作为未来独立评估的扩展方向，但不属于 v0.4.x 核心路线。

## 3. 目标用户与核心场景

### 3.1 目标用户

- 使用不止一家模型服务，或者经常更换模型的用户；
- 自己配置 API Key、服务地址、模型名称和生成参数的用户；
- 需要按用途管理不同助手、人设和会话的用户；
- 重视本地数据、备份、迁移和配置可控性的用户；
- 希望使用界面简单、功能边界清晰，但不希望被单一模型厂商绑定的用户。

### 3.2 核心使用路径

1. 用户在管理区域配置服务商、API Key 和模型。
2. 用户创建或选择一个助手/角色，设置人设和默认模型。
3. 用户进入统一聊天界面，发送文字、图片或受支持的附件。
4. 用户可以停止、重试、编辑、重新生成、切换分支和复制内容。
5. 用户在需要时启用联网搜索等可选能力；百川清楚说明该能力是否已配置、当前模型是否支持以及本轮是否开启。
6. 用户可以查看、管理和备份自己的会话及相关数据。

任何功能如果不能自然地服务于这条路径，就不应抢占近期开发资源。

## 4. 产品结构与导航原则

### 4.1 核心信息架构

- **消息**：助手列表、创建助手、进入对话。它是应用的主要入口。
- **管理**：服务商与模型配置、当前可用的扩展管理入口。只展示已经具备实际功能的项目。
- **我的**：通用设置、外观、搜索配置、存储与备份、错误记录、关于百川。
- **发现**：只有在存在真实、可用且无需虚构云端服务的内容时才占据一级导航。若当前只是占位页，应暂时从底部主导航收起；现有插件安装和本地扩展入口可留在管理区域。

导航数量不是产品目标。一级入口必须有明确用途；不可点击、没有内容或只显示“即将推出”的页面，不应占据主导航位置。

### 4.2 聊天页面原则

- v0.4.x 只维护一套默认聊天页面，以现有微信式扁平风格为基础。
- 聊天页的标题栏、消息列表、消息操作、输入区、错误展示和滚动规则必须共用。
- 角色/助手设置仍可从聊天页进入，但 Agent 自主工具执行入口暂时移除。
- 用户不应因为切换模型而看到另一套聊天布局或失去常用操作。

## 5. 功能分级

| 层级 | 内容 | 决策 |
|---|---|---|
| 核心能力 | 多模型连接、统一聊天、流式输出、停止/重试、消息编辑与分支、Markdown、图片/附件、本地会话、备份恢复 | 必须可靠 |
| 产品特色 | 助手/人设管理、模型能力识别、会话级搜索开关、记忆、使用配置 | 逐步完善 |
| 扩展能力 | 插件配置、角色卡/主题扩展、TTS 等已具备基础的可选能力 | 不得干扰核心聊天 |
| 暂缓探索 | Agent 工具执行、MCP 工具调用、代码插件执行、复杂自动化、插件市场 | v0.4.x 不扩张 |

### 特别说明

- **保留助手系统，不等于保留 Agent 执行。** `AgentEntity`、角色设定、助手列表和助手关联会话是百川的组织方式，应保留。
- **移除 DeepSeek 式独立 UI，不等于移除 DeepSeek 模型支持。** DeepSeek API 适配、搜索、TTS 或其他已实现的服务能力应独立评估并保留。
- 暂停实验性执行时，不删除旧数据库表、授权记录和运行记录；先用功能开关隔离，兼容旧版本数据。

## 6. 体验原则

### 6.1 顺手优先

用户点击后必须立即得到清晰反馈。请求尚未完成时，界面要表达“正在准备 / 正在生成 / 正在停止”，不能让按钮失去响应，也不能误导用户再次点击。

### 6.2 入口真实

有箭头、有按钮样式或有图标暗示可点击的控件，必须有真实动作；暂不可用的功能要隐藏或明确禁用，不允许空回调。

### 6.3 一致性

同一个操作在所有页面使用相同名称、位置逻辑和反馈方式。模型切换不应改变发送、停止、复制、删除、分支切换等基本操作。

### 6.4 可读性

长回复、Markdown、代码块、引用和列表应适合移动端阅读。消息内容不能被原始协议标记、模型内部字段或过度装饰打断。

### 6.5 可恢复

请求失败时尽可能保留草稿；删除、导入、迁移和备份等数据操作必须有明确语义和失败保护。

### 6.6 降低惊扰

用户主动上滑阅读时，不应被自动滚回底部；切换分支不应无故跳到页面顶部；键盘弹出不应遮挡输入区。

## 7. 视觉与交互方向

- 保留现有微信式扁平视觉方向，不进行整套推倒重画。
- 继续采用统一的浅色/深色语义 token；品牌色用于选中、链接和重要操作，不要让每个图标都抢主色。
- 延续清晰的信息层级、适度紧凑的列表、稳定的间距和一致的图标语言。
- 所有主要触控控件最小热区 48dp；图标可以小，热区不能跟着缩小。
- 动效用于解释状态变化，不用于装饰。普通局部反馈短促、轻量；不得用复杂模糊或连续动画拖慢低端设备。
- 液态玻璃或其他新视觉风格不进入 v0.4.0。

## 8. 数据、安全与信任

- API Key 等凭据继续由安全存储方案保护，不进入普通明文日志或普通备份。
- 本地数据优先；任何数据删除、迁移和导入都要有清晰边界与回滚策略。
- 用户界面不显示原始 HTTP 响应体、供应商内部 request_id 或未处理的协议异常。
- 模型的内部推理字段不作为普通聊天内容展示；如某供应商要求在后续请求中回传特定协议字段，应由适配层作为非 UI 元数据单独处理。
- 记忆是上下文辅助，不是每轮都要执行的命令。应区分偏好、事实、项目背景和明确指令，并控制无关记忆注入。

## 9. v0.4.x 版本方向

| 版本 | 定位 | 主要目标 |
|---|---|---|
| v0.4.0 | 核心对话与体验收敛 | 单一聊天 UI、消息链正确、输入区可靠、触控反馈、错误与 Markdown、发布可复现 |
| v0.4.1 | 体验验收与补齐 | 自动化回归、TalkBack/IME、窄屏和字号、性能与真机问题修复 |
| v0.5.0 | 多模型管理完善 | 服务商/模型配置易用性、能力识别、连接状态与配置诊断 |
| v0.6.0 | 数据体系完善 | 备份恢复、数据迁移、附件管理和记忆管理体验 |

版本目标是交付边界，不是强制日期。任何版本都不能以“功能已接入”代替“用户能稳定使用”。

## 10. v0.4.0 成功标准

v0.4.0 不以新增功能数量衡量，而以以下结果衡量：

1. 用户从消息页创建/进入助手、发送消息、停止、重试和切换分支的过程连贯，没有空操作。
2. 快速连点不会重复创建请求；准备中可取消；失败后草稿和附件状态可预测。
3. 删除消息或切换分支不会生成非法 API 消息序列。
4. 图片-only 消息不会被上下文组装器丢弃。
5. 微信式聊天可正确显示常用 Markdown；原始 reasoning 内容与底层错误不会泄露到普通 UI。
6. 搜索等可选能力在统一输入区中有清楚状态，不会因移除另一套 UI 而失去入口。
7. 所有可见控件有明确行为；主要触控热区达到 48dp；键盘、滚动和安全区表现稳定。
8. 发布 APK 能追溯到干净 Git commit，并能从该 commit 重建。
9. 未完成的实机验收如实标记 NOT RUN，不以源码改动或截图代替动态验证。
