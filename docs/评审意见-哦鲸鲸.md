# 评审意见 · 百川《计划.md》v0.1.0-plan

- 评审：哦鲸鲸（计划与方案协作）
- 日期：2026-11-07
- 对象：`docs/计划.md` v0.1.0-plan
- 依据：工程总提示词、《注意事项与免责说明》、发起者已确认的决策
- 说明：本文只做补充与风险提示，不推翻已定技术栈和第一版范围。

## 一、总体判断

计划的基础是扎实的：环境验证做到了可复现的程度（aapt2 移植、最小 APK 构建、统一构建脚本），技术栈与目录划分和总提示词方向一致，数据库骨架已覆盖大部分实体，七阶段划分也基本对得上原文第十二节。真正的短板不在"有没有写"，而在三处：第一版范围里有几项能力没有阶段落点（自动消息与通知、UI 三种风格、用户数据删除），数据库缺了几列关键字段（分支活跃指针、用量统计、智能体级参数与授权、软删除标记），部分验收标准停在"能跑"而没有可判定条件（兼容性、导入一致性、上下文压缩）。这些单看都不大，但都会在阶段二到阶段五引发返工，建议阶段一动工前一次补齐。另外计划第 0 节仍写"等待确认技术栈、阶段一尚未开始"，与发起者已确认并进入阶段一的口径不一致，开工时请同步状态表和第 9 节待决事项。

## 二、必须补充的需求点

### P0

**1. 自动消息与消息通知没有阶段落点**
- 现状：总提示词 3.4、3.5 属于核心聊天；计划建了 `scheduled_messages` 表，但七阶段表格里阶段二只到附件，阶段三只到记忆、压缩、TTS、搜索、错误系统，没有任何阶段负责实现和验收这块。
- 理由：自动消息横跨 WorkManager、通知渠道、系统权限、智能体停用状态和未读提示，最容易被"以后再说"推到阶段七仓促实现；它还会反向要求会话表增加未读字段。
- 建议落点：并入阶段三，或阶段二末尾单列。验收至少覆盖暂停/恢复、窗口外不发送、频率上限、智能体停用后不发送、通知权限被拒时的降级、应用被杀后的行为说明。

**2. UI 三种风格没有阶段落点，也缺少风格抽象层**
- 现状：第一版范围明确要求三种风格；计划全文只在风险表里出现一次"液态玻璃"，阶段表和目录结构没有对应交付项。
- 理由：三种风格不是最后贴上去的皮肤，它决定主题令牌、气泡布局、头像与名称是否显示、未读红点位置。阶段一若按单一风格写死，阶段二要重写所有页面。
- 建议落点：阶段一建立设计令牌与风格枚举（见 3.12），阶段二落地微信式与 DeepSeek 式两套聊天页，液态玻璃作为微信式变体放阶段二末或阶段三，并保留无模糊降级路径。计划里要写明每种风格第一版做到什么程度。

**3. 会话模型在三种风格下没有定义**
- 现状：`conversations` 表支持一个智能体多个会话；但微信式通常是一个智能体一个长期会话，DeepSeek 式是多会话列表。总提示词没有说明两种风格是否共用同一套会话语义。
- 理由：这是产品歧义，不是实现细节。它决定"消息"首页展示智能体列表还是会话列表、未读红点挂在哪一层、删除聊天记录删的是什么范围，也直接决定阶段二的数据结构与导航。
- 建议落点：阶段一结束前由发起者确认。实现上建议统一为"智能体下可有多个会话，微信式默认只用一个默认会话并隐藏列表"，两种风格共用一套表。确认结果写进计划。

**4. 模型配置流程的界面没有进入阶段二**
- 现状：阶段二写"模型适配（OpenAI 兼容 + 自定义地址）"，验收写"配置真实 API 后可完整对话"，但阶段表没有服务商、API Key、测试连接、模型列表这条配置链路。没有它，验收条件无法闭环。
- 理由：总提示词第四节把配置流程写成七个步骤，这是用户第一次使用百川的必经路径；它同时牵涉密钥存储、连接测试、模型能力识别，越晚做越容易和适配层脱节。
- 建议落点：阶段二明确包含"模型配置流程（表单、测试连接、模型列表获取或手填、默认模型选择）"，验收写清测试成功与失败两种表现。

**5. 插件更新回滚、接口版本兼容、用户授权状态没有落点**
- 现状：总提示词第七条要求更新失败回滚、接口版本兼容检查、不兼容明确提示、插件只能访问用户授权的资源；阶段五只写到安装、启用、停用、卸载、权限声明、数据隔离和内部测试插件，`plugins` 表也没有回滚与授权状态字段。
- 理由：这四项是未济接口可信度的核心。第一版不定下来，后面每个插件都要兼容历史版本，成本只会更高。
- 建议落点：阶段五补更新与回滚流程（保留上一版本包与数据快照）、`api_version` 兼容区间判定、`plugin_permissions` 授权表；内部测试插件增加"更新失败回滚"和"权限拒绝"两条用例。

**6. MCP 只有模块名，没有数据落点**
- 现状：总提示词要求 MCP 与未济接口分别管理权限和调用记录；计划有 `mcp/` 包和阶段五"MCP 管理基础"，但数据库没有任何 MCP 表。
- 理由：连接配置、工具清单缓存、调用记录都需要持久化。"分别管理权限和调用记录"是明文要求，只留一个包等于没设计。
- 建议落点：阶段五补 `mcp_servers`、`mcp_tools`、`mcp_call_logs`（见 3.8），验收写"连接、断开、调用一次工具并留下记录"。

### P1

**7. 用量与费用统计没有落点**
- 现状：总提示词要求缓存命中率、搜索调用次数和费用估算；数据库没有 token 或用量记录。
- 理由：这是官方 DeepSeek 优化的卖点之一，也是用户对成本有感知的前提。事后从消息内容反推 token 不可靠，必须请求时记录。
- 建议落点：阶段二记录模型调用用量，阶段三接入搜索统计（见 3.3）。

**8. 搜索来源没有持久化**
- 现状：要求"保留来源网址和必要的来源信息"，但消息只有文本内容。
- 理由：来源只活在当次响应里，重启后无法追溯，也无法在消息中展示引用。
- 建议落点：阶段三给消息加来源结构（`message_citations` 或 `messages.sources_json`），并保留查询词与结果记录。

**9. OP 协议"预留"的含义要写清**
- 现状：第一版范围写"OP 协议预留"，但协议定义待发起者确认；阶段二只写 OpenAI 兼容与自定义地址。计划没有说明"预留"具体指什么。
- 理由：不写清，要么开发模型在阶段二硬造一个协议实现，要么验收时被要求"支持 OP"而无法判定。
- 建议落点：计划里明确为"适配层留出协议枚举与接口位、配置项可填写但标记不可用、不进入阶段二验收范围"，协议文档到位后再补实现。

**10. 用户数据删除与附件治理缺失**
- 现状：总提示词要求"用户数据删除"，计划没有对应阶段与入口；附件、头像、备份文件都没有配额、清理、彻底删除的定义。
- 理由：删了数据库记录但文件还在私有目录，是最常见的"说删没删"；备份包里也会带走不该留的东西。
- 建议落点：阶段四增加"彻底删除（记录 + 文件 + 插件数据）"验收；阶段二定义附件大小上限与发送前压缩策略。

**11. Agent 的权限矩阵与同意记录不足**
- 现状：阶段六只写"权限模型、确认流程、工具调用基础设施、10 秒阅读门槛"；免责说明明确 Agent 会"操作文件、控制屏幕"，但计划没有列这两项分别对应哪些 Android 能力、两级权限各能做什么。
- 理由：权限等级如果只有名字没有清单，"授权系统操作"会被实现成宽泛授权，与"不得解释为无限制系统访问"直接冲突；同意记录也需要版本化，说明更新后要重新确认。
- 建议落点：阶段六前先出 `docs/Agent权限.md`（能力清单与授权范围），数据库加 `agent_consents`、`agent_runs`、`agent_actions`（见 3.9）；免责说明原文作为资源文件原样打包，保留署名与日期；10 秒门槛用可注入时钟实现，否则无法测试。

**12. 提示词组装与消息状态机没有规范**
- 现状：设计约定写了"时间元数据不拼进前缀"，但没说明谁负责组装、分段顺序、记忆与压缩摘要插在哪、分支切换后上下文取哪条路径。
- 理由：这是缓存命中率能否达标的关键，也是阶段二、三、五都会改的公共逻辑。没有规范，每个功能各拼一段，最后无法维护。
- 建议落点：阶段二产出 `docs/提示词组装.md` 与统一的 PromptAssembler，固定"系统/人设 → 记忆摘要 → 压缩摘要 → 最近消息 → 时间元数据（独立字段）"的分层；同时定义 `messages.status` 的完整枚举（生成中、成功、失败、已取消）。

**13. TTS 与语音范围需要收紧**
- 现状：总提示词写"支持 TTS 和语音相关能力"，阶段三只有"TTS 接口"。
- 理由："语音相关能力"没有边界，容易被理解成语音输入、变声、实时通话。
- 建议落点：第一版明确为"系统 TTS 播放 + 云端 TTS 适配预留，不做语音输入和实时语音通话"，写进范围；阶段三验收写"未配置 TTS 时文字聊天不受影响"。

### P2

**14. 首次启动引导**：没有任何配置时进入聊天会直接失败。建议阶段二加一个最小引导（配置服务商 → 选模型 → 开始聊天），或至少让"消息"页空状态直达配置入口。

**15. 深色模式与字号适配**：三种风格必然涉及明暗主题；Compose 的字体缩放与无障碍也属于 UI 验收。建议阶段一的设计令牌同时定义明暗两套，阶段二验收加"系统字体放大 1.3 倍不截断"。

**16. 三风格下的未读提示差异**：微信式在头像上点红点，DeepSeek 式不显示头像，需要另一种未读表达。建议和风格一起在阶段二定义，不要等阶段三做通知时再补。

## 三、数据库/架构建议

### 3.1 消息分支（`messages`、`conversations`）

- `messages.parent_id` 只建了树，没有"当前选中哪条分支"的指针。重新生成后无法确定会话该显示哪条路径，也无法切回旧分支。
- 建议：`conversations.active_leaf_message_id`（可空）记录当前路径末端；`messages` 增加 `sibling_seq`（同一 parent 下的稳定排序，避免同秒创建顺序漂移）、`deleted_at`、`updated_at`。
- `parent_id` 是自引用外键，首条消息为空。删除分支建议在应用层处理整棵子树，不要依赖数据库级联。

### 3.2 智能体参数与授权（`agents`、`aux_bindings`）

- `agents` 缺 `enabled`（停用，区别于 `blocked` 拉黑）、`deleted_at`（计划写"删除为软删除"，表里没有这一列）、采样与思考参数（温度、推理深度、上下文策略、流式开关）。建议加 `generation_json`，不要把这些塞进提示词。
- `aux_bindings` 缺 `agent_id`，无法表达"每个智能体设置独立模型与辅助模型"；也缺备用绑定（搜索是官方优先加备用，需要顺序或 `role` 字段）。建议改为 `agent_aux_bindings`，`agent_id` 可空表示全局默认，唯一约束 `(agent_id, capability, role)`。
- 缺"智能体可使用的插件"授权表：`plugins.permissions_json` 是插件声明，不等于某个智能体被允许调用。建议 `agent_plugin_grants(agent_id, plugin_id, granted, granted_at)`。
- `models.capabilities_json` 的能力来源要定：建议"内置常见服务商模板 + 用户手动覆盖"，不要试图从模型列表接口自动推断。

### 3.3 用量统计（新增 `api_usage`）

字段建议：`id, scope(model/search), provider_id, model_id, conversation_id, message_id, request_kind, prompt_tokens, completion_tokens, cached_tokens, reasoning_tokens, cost_estimate, latency_ms, success, created_at`。

用途：缓存命中率、费用估算、搜索调用次数、错误分析。聊天消息里只存最终文本，不要把用量塞进 `content`。

### 3.4 压缩摘要（新增 `conversation_summaries`）

字段：`id, conversation_id, up_to_message_id, summary, token_count, model_id, created_at`。

`memories` 是长期记忆，压缩摘要是一次性的上下文替代，两者不要混用；保留 `up_to_message_id` 才能做"压缩到哪一条"和回退。

### 3.5 未读与通知（`conversations` 或新增 `notification_events`）

最小方案：`conversations.last_read_message_id` / `last_read_at`。

若要支持朋友圈等未来插件复用统一通知，建议 `notification_events(id, channel, source_id, agent_id, title, body, created_at, read_at)`，第一版只用智能体主动消息一个 channel。

### 3.6 自动消息（`scheduled_messages`）

缺 `next_run_at`、`last_run_at`、`failure_count`、`work_id`（与 WorkManager 的映射）、`last_generated_message_id`（定时发送已生成内容时要知道发哪条）。

建议按 `agent_id` 建索引；`mode` 定义为枚举（发送已生成内容 / 调用模型生成），不要用自由文本。

### 3.7 插件（`plugins`、`plugin_permissions`、`plugin_data`）

- `plugins` 缺 `install_path`、包哈希或签名、`previous_version`（回滚用）、`api_version_min/max`、`disabled_at`。
- 新增 `plugin_permissions(plugin_id, permission, granted, granted_at)`。
- `plugin_data` 缺唯一索引 `(plugin_id, key)`；建议加 `type`、`size`，为未来图片类插件数据留位。
- 架构上：插件数据不要放 `baichuan.db`。总提示词要求插件异常不影响主聊天、插件有独立数据空间；同库意味着一个插件写坏库会波及核心。建议核心库 `baichuan.db` 加插件库 `plugin_store.db`（或按插件分文件），备份时统一打包。

### 3.8 MCP（新增三张表）

- `mcp_servers(id, name, transport, endpoint, headers_ref, enabled, last_status, last_connected_at)`
- `mcp_tools(id, server_id, name, description, schema_json, enabled)`
- `mcp_call_logs(id, server_id, tool_name, arguments_digest, result_digest, success, error_code, duration_ms, created_at)`

凭据用引用，不落明文；参数与结果存摘要或脱敏内容，避免把用户数据写进日志。

### 3.9 Agent 审计与同意（新增三张表）

- `agent_consents(id, doc_version, accepted_at)`：免责说明版本化，文档更新后重新确认。
- `agent_runs(id, agent_id, goal, permission_level, state, started_at, ended_at, cancel_reason)`
- `agent_actions(id, run_id, tool_name, args_summary, confirmed, result_summary, created_at)`：满足"执行记录"和"重要操作必须确认"。

### 3.10 软删除与索引

- 统一约定：`agents`、`conversations`、`messages`、`error_events` 用 `deleted_at`；物理删除只由"彻底删除"入口触发。
- 建议索引：`messages(conversation_id, created_at)`、`messages(parent_id)`、`error_events(agent_id, created_at)`、`memories(agent_id, pinned)`、`api_usage(created_at)`。

### 3.11 文件与 URI 存储

- `attachments.uri`、`agents.avatar_uri`、`agents.background_uri`、`conversations.background_uri` 如果存绝对路径或 `content://`，恢复备份或重启后可能失效。
- 建议：私有目录内用相对路径加统一 MediaResolver 解析；外部选择的图片在导入时复制进私有目录，不长期依赖 content URI 授权；备份 manifest 用相对路径，导入时重映射。附件按 `attachments/<conversation_id>/` 分目录，便于按会话删除和选择性备份。
- Android 14 起媒体读取与照片选择器有差异，建议用系统照片选择器，不申请全盘存储权限。

### 3.12 模块化口径与目录

- 计划 3.2 写"模块化（`:app` / `:core:*` / `:feature:*`）"，但第 4 节目录是单个 `app/` 模块内的包分层，两处口径不一致。
- 建议第一版明确为"单 Gradle 模块 + 严格包边界 + 接口隔离"。理由是当前构建内存约 2.5 GB、增量构建 4 到 5 分钟，多模块会显著增加构建与配置成本；功能稳定后再拆 `:core:data`、`:core:network`。第 6 节依赖图请注明是逻辑依赖，不是 Gradle 模块。
- 目录上 `app/app/src` 的嵌套容易混淆，可考虑 Gradle 根目录改名 `android/`，低优先级。

### 3.13 迁移与 schema

- 阶段一写"数据库与迁移框架"，但没有验收条件。建议：`exportSchema = true`、`schemas/` 纳入版本管理、用 MigrationTestHelper 覆盖"空库到 v1"、外键与 WAL 实测、`install -r` 覆盖安装不丢数据。
- 阶段一只落最小表集（`agents`、`conversations`、`messages`、`attachments`、`settings`），其余表随阶段新增，避免阶段一一次建全再反复迁移。

### 3.14 备份格式规范

- 阶段四前先出 `docs/备份格式.md`：manifest 字段（格式版本、软件版本、创建时间、数据类别、文件清单、每文件 SHA-256、总大小）、单包与文件夹的等价结构、凭据加密块的参数与口令派生方式、选择性备份的维度（智能体、会话、类别、时间范围）。
- 明确"恢复前自动备份当前数据"的落点：保留一份、容量上限、失败时如何回退。

### 3.15 凭据存储先验证再实现

- 计划写 EncryptedSharedPreferences。该库所属的 androidx.security-crypto 近年维护停滞并已有废弃标注，不建议在阶段二直接依赖。
- 建议阶段一花半天做最小验证：Keystore 加 AES-GCM 自行封装，或 Tink。选定后写进 `docs/架构.md`，并加一条测试断言"日志与普通备份中不出现明文 Key"。

## 四、阶段计划调整建议

### 4.1 阶段一增量

- 设计令牌与风格抽象（为三种风格留位）；日志与脱敏基础设施；DataStore 设置存储；最小表集加 schema 导出与迁移测试；版本锁定矩阵（Kotlin、Compose Compiler、KSP、AGP、aapt2 移植版）和一次真机安装验证。
- 状态表同步：技术栈已定，第 9 节第 1 条可以关闭。

### 4.2 阶段二增量

- 增加模型配置流程界面、非流式输出、请求取消与失败态、通知的最小打通（先不做自动发送）、两种风格的聊天页、`docs/提示词组装.md`。
- 验收写清：流式逐字、非流式完整返回、取消后状态正确、401、超时、断网三种错误表现、温度与推理深度能传到适配层并在界面生效、编辑与重新生成产生两条分支且可切换、切回旧分支后上下文正确。

### 4.3 阶段三调整

- 改名为"辅助能力与消息主动能力"，把自动消息与通知并入；补充搜索来源持久化与调用统计；上下文压缩写明触发阈值、压缩后原文保留策略、未配置辅助模型时的降级。
- 前置依赖：自动消息需要智能体"停用"状态，`agents.enabled` 要在阶段二建表时就加进去。

### 4.4 阶段四与阶段五的顺序

- 备份要求包含"插件配置和数据"，但插件在阶段五才实现，当前顺序会让阶段四的"往返一致"缺一类数据。

### 4.5 阶段五与阶段六的接口前置

- 建议在阶段五把"工具调用接口"（ToolProvider）与 MCP 一起抽象出来，阶段六只做 Agent 编排、权限与确认流程。否则阶段六会反过来改 MCP 和插件接口。

### 4.6 阶段七调整

- 单 HTML 演示从阶段二起增量维护，阶段七只做收尾，不要最后一次性补。
- 兼容性表述收敛：目前只有一台真机，先记录其 API 级别，写"实测范围 + 静态兼容核查范围 + 未覆盖范围"，不要在计划里出现无法证实的"兼容性测试通过"。这是总提示词第十三条的要求。
- 增加升级路径测试：用 `install -r` 覆盖安装验证数据迁移，不要先卸载再装。

### 4.7 每阶段通用门禁

- 建议在阶段表外单列一节"阶段门禁"：构建通过、真机安装成功、核心路径回归、计划.md 更新、遗留问题清单、下一步任务。每阶段执行，不必重复写进每个阶段。
