| 导出时附件全量进内存 | CONFIRMED（方案未单列） | `collectEntries()` `:114-119` 对每个附件 `readBytes()`，几百 MB 备份会直接 OOM |

**补充问题（方案漏掉）**：

1. **备份类别不覆盖 Agent、插件、MCP**。`CATEGORIES` 只有 chat/agents/memories/settings/attachments（`:54-57`），而数据库里已有 `agent_consents`、`agent_runs`、`agent_actions`、`plugins`、`plugin_permissions`、`plugin_data`、`mcp_*`。恢复后 Agent 授权丢失、插件全部消失、MCP 配置丢失，与"备份包含插件配置和数据"的总提示词要求冲突。这一项需要产品确认（见第九节）。
2. **恢复后的 `attachments.uri` 可被用于读取任意文件**。恢复时把备份里的路径原样写进 `attachments.uri`，聊天侧 `AttachmentStore.readBase64()` 用 `File(filesDir, relativePath)` 读取并 base64 发给模型。攻击者构造 `attachments.uri = "../databases/baichuan.db"` 的备份，用户一旦引用该附件，数据库内容就会被送到模型服务端。方案只写了写入穿越，没有写读取侧的数据外泄路径，建议在恢复校验里同时拒绝 `attachments.uri` 和 `avatarUri/backgroundUri` 的越界路径。
3. **快照文件不清理**。每次导入在 `cacheDir` 留一个 `pre_restore_*.zip`，失败回滚后也不删，容量会累积。
4. **文件夹备份选择逻辑**：`findBackupDir()` 自动选名称最新的目录，用户无法选择要恢复哪一个。多份备份时容易恢复错，应先列出候选让用户选。

## 六、方案漏掉的问题

按严重度排列，前三条建议直接进 P0。

1. **授权即全量路由**：`ChatViewModel.kt:310-313`。授权 Agent 后普通聊天被无条件接管。这是产品级回归，比状态机更紧急。修复方式：删掉这段分流，改成显式入口（输入区菜单或"用 Agent 执行"按钮），任务与普通消息分开。
2. **`fallbackToDestructiveMigration()` 与已修复的 AppContainer 冲突**：数据库迁移失败仍会静默清库，恢复界面形同虚设。两处必须一起改。
3. **备份恢复后的附件路径可用于读取任意文件**：写入穿越之外，`attachments.uri` 的越界值会让聊天把数据库内容 base64 发给模型。恢复校验要同时覆盖 `attachments.uri`、`avatarUri`、`backgroundUri`。
4. **备份类别不包含 Agent 授权、插件、MCP**：恢复后行为与备份前不一致，授权丢失却仍显示智能体。需要产品决策，见第九节。
5. **`AgentManager.requireAuthorized()` 是死代码**：`:47-51` 定义了但没有任何调用，授权校验只发生在 runner 开头一次。要么接进执行链，要么删掉。
6. **`docVersion` 不校验**：免责说明版本升级后，旧授权仍有效（`AgentManager.isAuthorized` 只判断记录存在）。方案 19 提到"说明文案更新后重新确认"，代码没做。
7. **插件权限只展示不执行**：`pluginPermissionDao` 只用于界面展示，运行时没有任何权限检查。配置型插件目前只读 `theme.json`/`presets.json`，问题不大，但"权限声明"与真实能力不一致，需要在未济接口文档里写清第一版权限只是声明。
8. **插件数据仍在主库**：`plugin_data` 表与核心表同库，插件写入异常会影响核心数据库。与"插件异常不得影响主聊天"的原则有冲突，建议后续拆独立库。
9. **Agent 使用非流式请求**：长任务期间用户只能看到"正在调用工具…"，没有中间步骤与耗时。方案 6 没提，体验上会像卡死。
10. **错误中心写入不完整**：Agent 失败与未知异常不写 ErrorEvent，用户只能看到消息上的失败，错误中心里查不到。
11. **备份快照文件不清理**：`cacheDir/pre_restore_*.zip` 只增不减。
12. **主动消息无法与普通消息区分**：消息表没有来源标记，UI 无法标注"主动消息"，与方案 10 最后一条冲突。
13. **无测试目录**：`src/test`、`src/androidTest` 都不存在，方案要求的所有测试目前为零。这是里程碑 A 的前置条件，不是收尾工作。

## 八、测试策略

当前没有任何测试设施，建议按"先 JVM 单测，后仪器测试"推进。

**插件**：把 ZIP 构造抽成测试工具，用 `ZipOutputStream` 生成恶意样本（`../outside.txt`、绝对路径、反斜杠、NUL、重复 entry、超长路径、超大 entry、截断包、manifest 缺字段）。断言：安装抛异常、插件目录外无文件、旧插件仍可加载。测试放在 `src/test`，不需要 Android 运行时。

**备份**：状态机每个阶段一条测试（结构校验失败、哈希失败、快照写失败、DB 事务失败、附件写失败、进程中断模拟）。负向样本包括：未声明 entry、重复路径、路径穿越、categories 非法、formatVersion 为 0 或负数、外键不一致。往返测试要覆盖"导出→清库→导入→逐表比对"，附件用哈希比对。

**数据库**：用 `MigrationTestHelper` 从 v1 逐级升到 v6，每个版本准备真实关联数据；再补一条"迁移 SQL 故意失败"用例，断言原库仍可打开、恢复界面出现。

**Agent**：状态机用纯逻辑测试覆盖所有转移；授权用 fake DAO 注入，模拟"运行中撤销"；取消用 `TestScope` 在模型请求、工具执行、两轮之间三个点取消；上下文用固定消息树断言传给 adapter 的消息序列；工具参数用畸形 JSON 覆盖。

**聊天**：`ChatViewModel` 用 fake repository/adapter，覆盖 send 附件失败、搜索失败、停止、错误写入；UI 用 Compose 测试覆盖搜索开关、思考面板、操作栏。

**网络**：SSE parser 用固定字节流覆盖多行 data、CRLF、注释行、`[DONE]`、末尾无换行、UTF-8 分片；适配器契约测试用 mock server 覆盖 401/429/5xx/空响应/畸形 JSON。

**UI**：真机截图按方案 11.5 的清单，浅色深色各一组；对比度用工具检查；动态字体 1.3 倍。

**测试纪律**：先写失败用例再改实现；每个 P0 项独立提交，提交信息带风险编号；报告中严格区分 PASS/FAIL/NOT RUN/BLOCKED。

## 九、需要发起者确认的取舍点

以下四项是方案明确要求"暂停并提问"的，建议在批次 0 结束前一次性确认。

**1. 权限等级语义**

现状是 A（仅操控 APP）/B（授权系统操作）两档，但工具只有 3 个只读工具，B 级没有任何额外能力。三个选项：

- 收敛为一级"只读辅助"，删掉 B 档，等真实系统工具就绪再加；
- 保留 A/B，但 B 档标注"实验性规划中"并禁用；
- 保留 A/B，B 档先接入一个低风险系统能力（如读取通知）做验证。

需要发起者定。**我的建议是第二个**：保留入口、禁用 B 档，避免权限错觉，也不删产品预期。

**2. 备份格式兼容**

当前 `FORMAT_VERSION = 1`，只拒绝过新版本。需要确认：

- 是否借这次整改把格式升到 v2（加入 Agent 授权/运行记录、插件、MCP 类别）？
- v1 备份是否必须继续可导入？如果需要，要写 v1→v2 的转换；
- 备份是否包含 Agent 授权与运行记录？包含的话，恢复后授权状态如何处理（直接生效还是要求重新确认）？

**3. UI 规范冲突**

方案要求严格按两份视觉规范落地，但现状与规范有差距：

- 液态玻璃（`wechat_glass`）只有枚举没有实现，是否本版必须交付？如果必须，低端机降级路径怎么定义？
- DeepSeek 风格已按官方结构实现（思考轨、操作栏、输入卡），与仓库现有《视觉规范-DeepSeek风格》是否一致？不一致时以哪份为准？
- 方案 11.3 要求 Agent 授权页、备份恢复页有专门验收点，这两页当前设计是否需要先出规范？

**4. 不可逆数据操作**

- 数据库恢复界面的"重置本机数据"是否本版提供？文案与二次确认方式需要定；
- 备份导入是"覆盖"还是"合并"？覆盖哪些类别、用户确认文案怎么写；
- Agent 运行记录删除、插件卸载时删除数据，是否都按"二次确认+明确范围"处理。

**补充三项，建议一并确认：**

5. **Agent 的调用语义**：授权后是"每条消息自动用 Agent"，还是"用户显式选择用 Agent 执行"？当前代码是前者，我建议改成后者，这决定聊天页入口形态，影响批次 2 的实现。
6. **搜索失败策略**：静默退化为普通回答，还是明确提示"本轮搜索失败"？涉及是否向用户暴露搜索计费。
7. **主动消息被拉黑后**：计划是暂停保留、还是删除？恢复拉黑后是否自动继续？

以上第 1、2、4 项会直接改变数据格式或不可逆操作，建议先确认再动批次 1；第 3 项影响批次 4；第 5 项影响批次 2，可以并行确认。
