# 百川 v0.3.1 源码与录屏专项审查报告

**审查对象**：`baichuan-0.3.1-test.apk`、2026-11-15 用户提供的 38.386 秒屏幕录制、GitHub `v0.3.1-test` 标签源码。  
**结论等级**：测试版可继续体验，但暂不建议把它视为已完成稳定性验收的版本。  
**重要限制**：没有在本环境启动 Android 模拟器或控制用户手机；本报告中的交互结论来自用户录屏逐帧观察、APK 静态检查和公开标签源码审查，不是我亲自点按 APK 的动态测试。

## 1. 交付物核验与审查边界

### 1.1 APK 与公开 Release 一致

- APK 大小：11,812,836 bytes。
- SHA-256：`30dd5d7b80bb3e441ff35ca9ffed6cd9ec0db0ab4323ffea083568c22af44e27`。
- 该哈希与 GitHub `v0.3.1-test` Release 所列 APK digest 一致，因此用户上传的 APK 就是该 Release 页面发布的同一份二进制文件。
- 录屏：1080 × 2412，60 fps，时长约 38.386 秒。

Release：<https://github.com/thecookfish1201-svg/baichuan/releases/tag/v0.3.1-test>

### 1.2 必须先解决的源码—APK 不一致

这是本轮审查中最重要的工程交付问题。

GitHub `v0.3.1-test` 标签指向 commit `59c1b81b750d6d71b5c5c21d0e535df2bb72eca4`。该 commit 的实际变更文件只有：

- `CHANGELOG.md`
- `README.md`
- `app/app/build.gradle.kts`
- `docs/鲸鱼娘-交互整改规格.md`

它没有提交 v0.3.1 Release notes 中声称的那批核心 UI / 状态机源代码改动。其父链中的 `5541264` 只给 `ChatViewModel.kt` 和 `AgentRunner.kt` 增加了 Agent 活动状态回调；再往后的 `afa0340` 主要更新截图验收记录。

另一方面，对上传 APK 的 DEX 字符串进行静态检查，能找到 `prepareJob`、`SnackbarHost`、`附件保存失败`、`正在停止` 等内容。这说明 APK 中确实包含部分公开标签源码没有体现的改动，较符合“从带有未提交修改的工作区构建 APK，再提交版本说明和标签”的情况。

仓库新增的 `docs/鲸鱼娘-交互整改规格.md` 自己也写明其依据是工作区 HEAD `a63be09` 加未提交修改，而不是 v0.3.1 标签的完整提交状态。

**判断**：APK 本身与 Release 文件一致，但当前 Git 标签并不能完整复现这份 APK。无法仅凭 `v0.3.1-test` 标签对 APK 中未提交的 P0/P1 修复逐行复核，也无法让其他开发者从标签源码可靠重建相同二进制。

**要求**：下一版发布前，先把 APK 对应的完整工作区源代码提交到 Git，再从该 commit 构建 APK、打标签、发布。不要再让“Release notes 已完成”替代“源代码已提交”。

## 3. P0 / P1 问题

### P0 — 不应把原始模型推理文本当作普通聊天内容展示

录屏 00:09–00:12 的“已思考”区域不只是简短的进度提示，而是直接显示了模型内部推理式文字，其中包含“我们需要回答用户”“根据历史摘要”等内部操作性内容。它还复述了长期记忆的具体指令。

这带来三类问题：

1. 用户看到的不是经过整理的解释，而是模型内部推理轨迹，阅读体验差且容易暴露提示词组织、记忆内容或其他内部上下文。
2. 该区域展开后占据聊天视口的大量空间，最终答复反而被挤到下方。
3. 把 `reasoning_content` 与公开回答混合展示，会让不同供应商的内部字段含义差异直接变成 UI 行为。

**建议**：默认不向普通用户展示原始 `reasoning_content`，也不要把它作为长期聊天内容保存供 UI 回放。可保留“思考中…”状态；若供应商明确提供面向用户的 reasoning summary，再展示经过定义和筛选的摘要。折叠默认态不是充分修复，关键是不能把原始内部推理当成产品输出。

### P1 — A/微信式 UI 没有搜索开关，用户实际无法启用会话搜索

公开源码中：

- `ChatUiState.sessionSearch` 默认 `false`。
- `toggleSearch()` 由 ViewModel 提供。
- C/DeepSeek 式 `DeepSeekChat` 输入区有“智能搜索”按钮，并接入 `onToggleSearch`。
- A/微信式 `ChatScreen` 的 `ChatInputBar` 没有搜索开关，也没有把 `toggleSearch` 传给输入区。

录屏在 00:27 明确显示微信式为当前选中样式。随后模型在推理区域表示当前会话看不到联网/搜索工具。这个行为与源码的功能分布相符：用户即使配置了网络搜索服务，也不等于当前会话已打开搜索能力。

**建议**：把“联网搜索 / 深度思考”等能力控件迁移到唯一、共用的 A 风格 Composer 或一个统一的“能力”菜单中。C 风格删除后，不能顺手把搜索开关一起删除。搜索配置和会话级开关要分清：一个负责服务可用，一个负责本次会话是否启用。

### P1 — 删除消息后可能生成不合法的上下文序列

公开源码中的逻辑组合存在风险：

1. `MessageDao.listByConversation()` 只读取 `deletedAt IS NULL` 的消息。
2. `ChatRepository.pathTo()` 从当前叶子沿 `parentId` 回溯；如果父消息已软删除，它在查询结果中不存在，回溯会提前终止。
3. `PromptAssembler.assemble()` 不验证第一条非 system 消息是否为 user，也不检查 user/assistant 的连续顺序，只把剩余路径按原样塞进请求。

例如，用户删除了某个 user 消息，但其后代 assistant 消息还保留并仍被选为当前分支叶子，那么下次请求可能从 assistant 消息开始。服务端就可能返回录屏中的 `an assistant message must follow a user message` 一类序列错误。

这与录屏中的 API 报错高度吻合，但**仅凭录屏还不能证明这一次具体就是删除父消息导致**；仍需结合发生错误时的数据库消息树和实际请求 role 序列确认。

**建议**：明确删除语义。若删除某条消息，应同步处理它的后代，或把当前分支回退到最近一个完整、合法的祖先节点。发送前再做协议级校验：第一条非 system 消息必须是 user；不能存在孤立 assistant/tool 消息；每个 tool 回复必须对应合法的 tool call。校验失败时在本地阻止请求，并提示用户切换分支或新建会话。

必须添加回归用例：删除根 user、删除中间 user、删除 assistant、删除当前叶子、切换到包含已删除祖先的分支后继续发送。

### P1 — API 原始错误文本直接显示给用户

录屏 00:30–00:36 显示了英文协议错误和 `request_id`。公开源码中的流式异常路径会把 `ModelException.message` 写入消息错误摘要，而消息气泡直接展示 `errorSummary`。

**建议**：用户界面只展示可执行的错误提示，例如“这段对话的上下文顺序不完整，无法继续发送。请重新发送或新建会话。” 原始 HTTP 错误、request_id、响应体摘要只进入脱敏的错误记录，供开发者定位。不要让用户自己阅读协议错误。

### P1 — 微信式消息正文没有调用 Markdown 渲染器

公开源码 `ChatScreen.kt` 的微信式 `MessageItem` 用普通 `Text(message.content)` 显示消息；C 风格才使用 `MarkdownText`。录屏中最终答复里的 `**看不到可调用的联网/搜索工具**` 等标记原样出现，正好与这一实现差异一致。

**建议**：统一一套消息正文渲染组件。A 风格保留气泡外观，但气泡内部也调用 Markdown renderer。第一阶段至少正确处理：粗体、斜体、行内代码、代码块、标题、无序/有序列表、链接、引用；无法支持的语法要有稳定降级，不能把 `**` 直接暴露给用户。

### P1 — 仅附件发送时，图片消息可能被 PromptAssembler 丢弃

`ChatViewModel.send()` 允许“文字为空但有附件”的消息；但公开源码 `PromptAssembler.assemble()` 在处理历史消息时只要 `message.content.isBlank()` 就跳过整条消息，即使 `imagesByMessage[message.id]` 中存在图片。这会让图片单独发送的用户消息从模型上下文中消失。

**建议**：保留 `content` 非空或 `images` 非空的消息。增加图片-only、文本+图片、文件附件等契约测试。这个问题不是录屏中出现的，但属于本轮源码审查发现。

## 4. P2 — 产品与交互收敛建议

### 4.1 只保留一套聊天 UI

录屏 00:27 的外观页已经能看出两套风格的设置入口。结合反复维护仍不稳定的情况，暂时去掉 DeepSeek 式独立页面是合理的工程取舍。

建议：

- 外观页只保留微信式 / 百川默认聊天布局。
- 启动时若发现旧设置 `ui_style = deepseek`，迁移为 `wechat`；不要因为用户升级而显示空白或进入不存在的页面。
- 合并两套页面的消息操作、错误展示、滚动、附件和 Composer 状态，不再维持两份聊天布局代码。
- **不要删除 DeepSeek 模型适配**。DeepSeek 是模型服务商，不等于 DeepSeek 式 UI。保留模型请求、推理参数、服务器搜索、TTS 等已经实现且有用户价值的服务端能力。

### 4.2 暂停的是“实验性 Agent 工具执行”，不是删除智能体/角色系统

百川目前的消息首页以智能体为会话入口。`AgentEntity`、角色人设、智能体列表和每个智能体的聊天会话，仍然是产品核心组织方式。

建议暂时移除/禁用的是：

- 聊天页的 Agent 模式切换按钮；
- AgentRunner 自动工具调用入口；
- Agent 工具权限授权、免责门槛和相关实验状态；
- 管理页“智能体权限”、我的页面“Agent 运行记录”等实验性入口。

保留：智能体创建/编辑、角色设定、智能体与会话的关联、已有对话记录。数据库中的 Agent runs / consents 等表先保留并继续支持旧数据读取或备份迁移；不要为了 UI 清理而直接删表、重置用户数据。服务层同时加硬性禁用开关，确保即使旧设置或旧数据库状态残留，也不能意外启动 Agent 工具。

### 4.3 导航与页面密度

录屏中消息首页只有一个智能体时，下半屏基本空白；发现页 / 插件页也比较接近框架占位。当前不需要大规模改版，建议：

- 消息列表非空时仍提供明确的新建智能体入口（例如顶栏 `+`），不要只在空状态显示创建按钮。
- “发现”页没有可用内容前，可以降低主导航权重或改为真正有用的扩展入口；不要长期显示“框架未启用”作为核心页面内容。
- 管理页只呈现当前真实可用的配置项；未实现的黑名单、权限管理入口应隐藏，而不只是灰化。
- 顶部工具类图标应有明确语义；若 Agent 模式移除，聊天页 wrench 图标一起消失，避免用户误以为还有实验功能。

### 4.4 长期记忆注入

录屏中的推理区反复围绕“梁文锋牛逼！大肥鱼吃白饭！”这一长期记忆指令展开。它说明记忆内容确实进入模型上下文，但也暴露出一个产品风险：把记忆一律作为高优先级 system 文字注入，容易让一条无关指令在每轮对话中反复主导回答。

建议把记忆区分为事实、偏好、当前项目背景和明确指令；默认只作为相关上下文，不让任意记忆自动成为每轮必须执行的命令。检索应按当前问题相关性选择，而不是简单把前 20 条全部拼接。记忆应允许查看来源、编辑、停用和删除。

## 5. v0.4.0 建议路线

**建议将 v0.4.0 定义为“单一聊天体验与可靠性版本”，不做功能扩张。**

### P0：先保证发布可复现

1. 将当前 APK 对应的完整源代码提交到 Git。
2. 建立干净工作树检查；发布脚本在 dirty working tree 时失败。
3. 从 tag commit 自动构建 APK；Release 附 commit SHA、versionName、versionCode、SHA-256。
4. 保存截图/录屏验收记录，不再将 NOT RUN 写成已验收。

### P1：统一聊天内核

1. 只保留一套聊天页面与一个 Composer。
2. `ComposerState` 是唯一任务状态事实源；`isStreaming` 由状态派生，不再两套 UI 各自判断。
3. 统一搜索、推理深度、附件、停止、重试和错误入口。
4. 统一 Markdown renderer，禁止原始 reasoning 进入普通消息正文。
5. 处理删除后分支完整性和 API message role 校验。
6. 修复图片-only 消息上下文丢失。

### P2：建立最小自动化回归

- Compose/ViewModel：快速连点发送只产生一次请求；PREPARING 期间停止不会偷跑请求；失败后草稿仍保留；成功/失败/取消都进入终态。
- PromptAssembler：正常历史、根消息删除、中间节点删除、分支切换、空文本图片附件、空白消息。
- Adapter：断言发送的 messages role 顺序；非法序列在本地被拦截；API 失败时 UI 不暴露 request_id 或原始响应体。
- UI：键盘弹出、IME Send、上滑阅读、错误 Snackbar、附件移除、删除确认、48dp 热区。

### P3：重新验收再决定扩展

完成 4 种基本场景：空会话、普通对话、长 Markdown 回复、网络/模型失败；再补浅色/深色、360dp 窄屏、字号 1.3x、TalkBack。以上未通过前，不重新加入 C 风格或 Agent 工具执行。

## 最终判断

v0.3.1 在用户录屏中已经能看出部分交互收敛：消息首页搜索图标消失、主题选择可见、未实现的管理入口不再都显示箭头，输入框占位也更准确。但这不是一次完整验收。

当前最重要的不是继续打磨动画或新增 Agent 能力，而是：**禁止原始推理展示、让 A 风格真正能启用搜索、修复删除/分支后的上下文序列、把 Markdown 和错误显示做好，并保证发布 APK 与 Git 源码一一对应。**
