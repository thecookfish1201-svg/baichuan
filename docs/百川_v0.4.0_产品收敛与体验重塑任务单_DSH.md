# 百川 v0.4.0 · 产品收敛与体验重塑任务单（DSH 执行版）

> 版本定位：**核心对话与体验收敛版**  
> 产品路线：个人 AI 对话工作台（路线 A）  
> 最高目标：让百川从“功能能跑”变成“日常用起来顺、可靠、可预期”。  
> 基线：v0.3.1 测试版、用户录屏审查、公开仓库 main 当前可读取源码、`docs/视觉规范.md`、`docs/UI_BASELINE.md`、`docs/鲸鱼娘-交互整改规格.md`。  
> 执行方式：先审计现状，再修改；已有功能必须先验证，不得盲目重写。

---

## 0. 给 DSH 的总指令

本轮不是功能扩张，也不是全盘换皮。请严格以《百川·产品章程 v1.0》为产品边界，优先修复对话链路和交互手感。保留现有微信式扁平风格，统一组件和行为，不要继续维护 DeepSeek 式独立聊天页面。

### 本轮必须交付的结果

1. 一套聊天 UI、一套 Composer、一套消息操作和错误反馈体系。
2. 发送、准备、流式、停止、失败、取消等状态互斥且可预测。
3. 消息树删除/分支操作不会生成非法上下文；图片-only 消息能正确进入请求。
4. Markdown、搜索、附件、停止、复制、编辑、重试、分支在统一界面可用。
5. 页面不再出现空回调、假箭头、无效主导航和未实现功能入口。
6. 触控、键盘、滚动、加载反馈、长文本阅读具有一致的“手感”。
7. APK、Git commit、版本号和构建记录一致，可追溯、可复现。

### 重要执行纪律

- 在开始修改前检查本地工作区、当前分支、HEAD、未提交更改和 APK 对应来源；不要假定本地工作区与 GitHub `main` 或 `v0.3.1-test` 相同。
- 先读取本任务单、产品章程、v0.3.1 专项审查报告和现有视觉/交互规格。
- `CHANGELOG.md` 中声称已修复的内容，不代表当前源码一定有该实现。逐项核对真实代码；若已实现，补测试证明，不要重复造轮子。
- 修改前建立独立分支，例如 `stabilize/v0.4.0`。不要直接在 `main` 上堆叠未审查修改。
- 每个阶段独立提交，提交信息说明“改了什么、为什么、怎么验证”。
- 禁止在 dirty working tree 上生成正式 Release APK。Debug 临时构建可以，但必须标明不是发布产物。
- 测试未执行就标记 `NOT RUN`；不得把“编译成功”写成“功能通过”。
- 保留数据库迁移、备份兼容和用户数据；本轮不因隐藏功能而删表或清空旧数据。

## 1. P0：基线审计与发布可信度

### 1.1 建立唯一可信代码基线

1. 记录当前分支、HEAD SHA、工作区 dirty 状态、Gradle/JDK/SDK 版本。
2. 检查用户提供的 v0.3.1 APK 对应的完整源码是否全部提交；将任何用于构建 APK 的未提交修改先整理成明确提交。
3. 对比本地工作区、GitHub `main`、`v0.3.1-test` 标签和 Release APK 的来源，不得混淆。
4. 建立发布前 dirty-tree 检查；工作区不干净时 Release 任务失败。
5. 构建产物记录 `versionName`、`versionCode`、commit SHA、构建时间和 SHA-256。
6. CI 至少执行静态检查、编译和单元测试；如环境无法执行，明确记录阻塞原因。

**验收**：任何一个 v0.4.0 Release APK 都能追溯至一个干净 commit；其他人按文档从该 commit 构建可得到同版本产物。字节级一致如受签名/构建环境影响无法保证，必须说明差异，不得虚称完全可复现。

### 1.2 先审计 v0.3.1 已完成项，避免重复劳动

重点对照 `CHANGELOG.md` 中的发送防重入、早退终态、附件清理、prepareJob、停止任务保护、Snackbar、ListRow 空回调等声明。逐项产出：

- 源码位置；
- 真实实现说明；
- 对应测试；
- 当前验证结果；
- 是否还需修改。

当前可读取的公开源码存在与变更记录不完全一致的迹象，例如 `ChatViewModel` 仍同时保存 `isStreaming` 和 `composerState`，`send()` 的部分守卫仍只检查 `isStreaming`，附件保存失败/消息落库失败分支需要核对是否恢复 Composer 终态；消息首页仍有搜索图标空回调。请以 DSH 当前实际 checkout 为准复查。

**验收**：形成 `docs/v0.4.0_BASELINE_AUDIT.md`，没有“根据 changelog 推测已完成”的项目。

## 2. P0：聊天内核正确性

### 2.1 Composer 必须只有一个状态事实源

现状风险：`ChatUiState` 同时包含 `isStreaming` 与 `composerState`，不同页面/分支可能用不同字段判断发送和停止；PREPARING 与 STREAMING 之间容易产生短暂状态不一致。

要求：

1. 以 `ComposerState` 作为唯一状态事实源：`IDLE / PREPARING / STREAMING / STOP_REQUESTED / COMPLETED / FAILED / CANCELLED`。
2. `isStreaming` 若为兼容需要保留，只能是派生值，禁止独立写入。
3. `send / regenerate / editAndResend` 使用同一任务入口和同一互斥守卫；不能各自维护一套竞态逻辑。
4. 用户触发发送时，必须在任何挂起/IO 之前原子进入 PREPARING；PREPARING、STREAMING、STOP_REQUESTED 时重复发送一律拒绝。
5. 准备阶段和流式阶段必须属于同一个可取消任务，停止操作能够取消当前准备/请求，不允许只取消已经开始的 streamJob。
6. 取消、失败、成功、无模型、会话丢失、附件保存失败、消息落库失败、网络断开等路径都必须进入明确终态。
7. 失败时保留文字草稿；附件是否保留要有一致规则。不得出现附件 UI 清空但文件落库失败，或文件已存储但消息未写入造成孤儿附件。
8. 没有活动任务时点击停止是无操作，不得把状态变成 STOP_REQUESTED。
9. ViewModel 清理时取消任务并释放资源；不得让旧会话任务污染新会话 UI。

**必须测试**：快速连点 3 次；PREPARING 阶段停止；STREAMING 阶段停止；附件部分失败；消息插入失败；模型未配置；网络异常；切换会话/离开页面时取消；失败后再次发送。

**验收**：每个用户动作最多产生一条 user 消息和一个请求；终态后按钮、草稿、附件和提示一致。

### 2.2 修复消息树与上下文角色序列

已知风险：软删除只标记当前节点，而 `listByConversation()` 排除已删除节点；`pathTo()` 可能无法找到已删除父节点，回溯提前终止。孤立的 assistant/tool 消息有机会进入下一次请求。

要求：

1. 明确删除语义。推荐删除节点后，其当前分支后代不再成为有效活动路径；可采用级联软删除，或把活动叶子回退到最近一个完整合法祖先。保留其他独立分支。
2. `pathTo()` 不能静默返回断裂路径；遇到缺失 parent、跨会话 parent、循环引用或已删除祖先时，返回明确的无效路径结果。
3. 发送前在统一层校验 `messages`：第一条非 system 消息必须为 user；不允许孤立 assistant/tool；tool call 与 tool result 必须正确配对；不能因过滤空白消息而留下孤立角色。
4. 校验失败时本地拦截，提示“当前对话分支不完整，请切换到其他版本或新建会话”，并写脱敏诊断日志。
5. 删除、编辑并重发、重新生成、切换分支都应走事务或可恢复的 repository 操作。
6. 不得通过简单清空历史来规避问题；要保留用户其他分支和对话数据。

**必须测试**：删除根 user；删除中间 user；删除 assistant；删除当前叶子；切换到有删除祖先的分支；编辑并重发后切换分支；重新生成后再发送；历史含空白占位 assistant；跨会话 parent 防护。

**验收**：所有生成的网络请求都有合法 role 序列；任何断链都在本地明确处理，不把供应商协议错误抛给用户。

### 2.3 图片-only 与附件消息完整性

已知问题：当前 `PromptAssembler` 对 `content.isBlank()` 的消息直接跳过，即使该消息包含图片附件，也会导致图片-only user message 丢失。

要求：

- 保留“正文非空 **或** 附件 payload 非空”的消息。
- 图片-only 必须以 user role 进入模型请求并包含图片 payload。
- 文字+图片应保持同一消息的内容与图片顺序。
- 文件附件要区分“已保存到本地”和“当前模型协议可实际读取”；如果模型不支持文件输入，发送前明确提示，不得假装文件已进入模型上下文。
- 附件 MIME、大小、路径读取失败都要有明确用户反馈和脱敏日志。

**必须测试**：纯图片、文字+图片、多图片、纯文件、附件读取失败、图片解码失败、附件保存失败、备份恢复后的附件路径。

## 3. P1：收敛产品功能边界

### 3.1 移除 DeepSeek 式独立聊天 UI

1. 外观设置中移除“DeepSeek 式”选项。
2. `ui_style=deepseek` 的旧用户数据迁移到 `wechat`；迁移必须幂等，升级后不闪屏、不白屏、不丢会话。
3. 移除 `DeepSeekChat` 页面及重复 Composer；整合所有确实有用的交互进入公共聊天页。
4. 清理只属于 C 页面且无其他引用的死代码、样式 token 和资源。
5. 不要删除 DeepSeek 模型适配、DeepSeek Search、TTS、模型参数或其他服务层能力。服务能力与 UI 样式必须解耦。
6. 不要把模型名称写死在通用 UI 控件中；通用能力显示为“联网搜索”“深度思考”等用户理解的术语。

**验收**：从旧版本升级后，原 C 风格会话在微信式页面打开；模型配置、消息、附件、分支和角色数据完整。

### 3.2 暂停 Agent 自主工具执行，但保留助手管理

暂停：

- 聊天页 Agent 模式切换（wrench/build 图标）；
- `AgentRunner.run()` 的普通用户执行入口；
- Agent 工具调用自动循环；
- 实验性 Agent 授权、免责阅读门槛、运行记录等主要导航入口。

保留：

- `AgentEntity`、助手创建/编辑、人设、模型绑定、助手列表和助手会话；
- 旧 Agent 数据表、授权、运行记录和备份读取兼容；
- 未来重新启用前需要的接口边界，但不开放普通用户触发。

要求：

1. 在服务层设置全局 feature flag，默认关闭；不能只隐藏 UI。
2. 即使旧数据库有授权、旧会话有 agentMode=true，也不能启动工具执行。
3. 旧数据不删除、不自动重置；用户仍能正常打开原助手和聊天记录。
4. 普通聊天不再依赖 Agent 授权查询，不应因 Agent 暂停增加启动延迟或报错。
5. 管理页/我的页隐藏 Agent 权限、免责确认、Agent 运行记录等实验入口；错误记录保留。

**验收**：普通构建中所有路径都无法触发 Agent 工具；已有助手与普通聊天不受影响。

### 3.3 保留现有核心能力，不做无关扩张

保留并验证：
- OpenAI 兼容模型适配；
- 服务商、模型和 API Key 配置；
- DeepSeek 等具体供应商适配能力；
- 会话、助手、人设与消息分支；
- 同舟备份、附件数据和错误记录；
- 已具备且稳定的 TTS/联网搜索入口。

本轮不新增：MCP 工具执行、代码型插件执行、Agent 写操作、插件市场、复杂工作流、跨设备云同步、新协议大规模接入、ASR/录音或液态玻璃 UI。

## 4. P1：唯一聊天界面与统一能力入口

### 4.1 Composer 统一结构

统一输入区应包含：

- 附件入口；
- 多行文字输入；
- 能力菜单（仅显示当前模型与服务配置可用的选项）；
- 发送/停止按钮；
- 已选附件预览与移除。

搜索状态必须明确区分：

1. 搜索服务未配置；
2. 搜索服务已配置、当前会话未开启；
3. 本轮已开启搜索；
4. 当前模型或接口不支持该能力。

不能只因为用户在“我的”中配置了搜索服务，就默认本轮搜索已开启。不能点击后无反应。深度思考只在模型/服务能力允许时可用，不支持时说明原因或隐藏。

### 4.2 搜索入口

当前微信式 Composer 缺少搜索开关，而 C 页面有 `toggleSearch()` 入口。删除 C 页面后，必须把会话搜索开关迁移到公共 Composer 的“能力”入口。

另外，当前公开 `MessagesScreen` 的顶部搜索图标使用空回调。v0.4.0 不做完整的会话搜索时，应直接移除这个空入口；不得保留一个点击无反应的搜索按钮。只有当真实搜索实现完成并通过验收后才能重新显示。

**验收**：微信式聊天可明确开启/关闭搜索；服务未配置、模型不支持、会话未开启三种情况均能准确表达。

### 4.3 统一消息操作

同一套操作规则用于所有模型：

- 用户消息：复制、编辑并重发、删除；
- 助手消息：复制、重新生成、删除、分享；
- 分支：保留当前版本信息和切换能力；
- 朗读：只有 TTS 确实可用时显示。

长按菜单可以作为主要入口，常用操作可保留少量轻量操作按钮。菜单用词统一，不允许同一功能在不同页面叫不同名字。删除继续二次确认；确认文案必须与软删除/分支保留的实际行为一致。

## 5. P1：对话内容可信与可读

### 5.1 原始 reasoning 内容不进入普通 UI

1. 不向普通用户显示原始 `reasoning_content`、模型内部分析字段或看起来像提示词/路由过程的文本。
2. 普通聊天 UI 不再提供可展开的原始“思考链”面板。
3. 可展示轻量状态：“思考中…”、“已完成”；只有供应商明确提供用户可见的 reasoning summary 时，才由独立字段与白名单规则渲染。
4. 如果供应商协议要求后续请求回传 reasoning 字段，适配层可按协议作为 opaque metadata 使用，但不能把它拼进普通消息正文、分享文本、通知或搜索索引。
5. 历史数据库中的 reasoning 字段不要在本轮升级时粗暴清空；先停止展示，保留兼容读取策略，并评估后续清理/导出规则。

**验收**：模拟含有“我们需要回答用户”“system prompt”“长期记忆指令”等内部文字的响应，聊天页面、通知、复制和分享均不得显示原始 reasoning。

### 5.2 Markdown 统一渲染

微信式气泡内部必须使用统一 Markdown renderer，不得直接把 Markdown 原文交给普通 `Text`。

首版支持：粗体、斜体、行内代码、代码块、标题、无序/有序列表、引用、链接。要求：

- 代码块使用等宽字体，可横向滚动；不破坏缩进；
- 长链接不撑破气泡；
- 列表缩进与行距清晰；
- 普通文字没有不必要的容器、阴影或多余间距；
- 未支持语法必须稳定降级，不裸露明显的 `**`、`###` 和围栏符号；
- 流式未完成的 Markdown 标记不得让整条消息反复大幅跳版。

**验收**：同一段 Markdown 在 360dp、标准手机和较宽屏幕显示正常；浅色/深色主题对比度合格。

### 5.3 错误对用户友好，对开发者有诊断

UI 不直接显示 `ModelException.message`、HTTP response body、request_id、原始 URL 参数或原始 JSON。

用户侧错误类别至少包括：
- 网络连接失败；
- API Key/认证失败；
- 额度或余额不足（若供应商错误可明确识别）；
- 请求频率限制；
- 服务端暂时不可用；
- 当前会话上下文不完整；
- 附件读取/保存失败；
- 本地数据读写失败。

用户侧给出可行动提示；错误记录保留脱敏后的原始诊断信息和 request_id。用户主动复制诊断信息时，提供明确的“复制诊断信息”动作，并在复制前过滤 API Key、授权头、私密 URL 参数和消息正文。

错误展示规则：全局操作错误走 Snackbar；具体消息生成失败走消息级提示；同一错误事件只能走一个出口，不重复弹两次。

## 6. P1：把“手感”作为明确交付目标

本章不是美术换皮，而是交互完成度要求。所有可见控件都要有清楚的触控反馈、加载状态、可用状态和完成状态。

### 6.1 触控反馈和点击语义

1. 所有主要按钮、图标按钮、列表入口、分支切换、附件移除、来源展开等可点区域，最小触控热区为 48×48dp。
2. 视觉图标可以是 18–24dp，但不能为了缩小图标而把 IconButton 热区也缩小。
3. 可点击控件有统一 ripple/pressed feedback；disabled 控件不得有 ripple、点击回调或导航箭头。
4. 有箭头就必须可导航；没有动作的行不应伪装成按钮。
5. 点击后本地 UI 状态立即反馈，不要等网络响应才显示按下、选中或准备状态。
6. 主要动作要有明确的文案和无障碍语义；图标按钮必须提供准确 contentDescription。

### 6.2 消息首页与导航

1. 当前消息页有内容时仍要有显眼但克制的“创建助手”入口（优先顶栏 `+`）；不能只有空页面才有创建按钮。
2. 移除当前无动作的顶部搜索图标，直到真正的助手/会话搜索完成。
3. 助手列表行保持统一：头像/标识、名称、人设摘要、状态；点击整行打开对应助手会话。
4. 列表密度按现有视觉规范执行：主列表双行约 72dp、单行约 60dp；设置类 ListRow 可按内容使用 64/56dp。系统字体放大时允许自适应增高。
5. 行高、图标、分割线、左右边距和按压反馈一致；图标以中性色为主，只有选中和重要操作用品牌色。
6. 一级“发现”如果仍只有空白/测试插件/占位文案，v0.4.0 暂时从底部导航收起。底层插件和本地扩展能力继续保留在管理区域；不建设虚构的云端市场。
7. 底部导航切换后页面状态合理保留；返回键行为符合 Android 导航预期，不应意外退出或回到错误页面。

### 6.3 管理与个人页去占位

1. 管理页只保留确实可用的服务商、模型、扩展/插件和其他配置入口。
2. 黑名单、Agent 权限、Agent 运行记录等实验性入口随 Agent 执行暂停而隐藏。
3. “设置”入口必须进入真实设置页；“关于”做轻量信息页/对话框，至少呈现应用版本、项目说明和项目地址。若本轮不做，必须隐藏，不得留空回调。
4. 我的页面展示真实状态，不用固定占位值；无法读取的数据就不显示，不编造数量和状态。
5. “发现”/插件空状态使用真实文案；不展示内部测试插件作为普通用户的核心推荐内容。
6. `ListRow` API 应把 `onClick` 设计为可空回调；禁止默认空 lambda + 默认箭头。调用点逐处检查：可用就接通，不可用就移除或明确 disabled/规划中。

### 6.4 聊天输入区手感

1. 输入框占位保持“发消息”；没有真正接入录音/语音识别前，不出现“按住说话”或无效麦克风。
2. 输入区支持自然多行，不因输入长文本而遮挡发送键；建议设置合理最大显示行数，超出后内部滚动。
3. 键盘弹出时输入区可靠上移，消息列表可滚动；系统手势区、三键导航和横屏都不遮挡。
4. IME Send 发送；Shift+Enter 换行；中文输入法组合态不能误发或截断候选词。
5. 有附件时附件条显示在输入区上方，移除按钮热区 48dp；附件名过长时省略，不撑破布局。
6. PREPARING 时发送按钮转为明确准备状态；STREAMING 时显示停止；STOP_REQUESTED 时禁用重复点并显示“正在停止…”；终态后恢复输入。
7. 文字草稿在网络错误、模型未配置、附件失败和消息落库失败时按预期保留。
8. Composer 与键盘之间不能出现大块无意义空隙，也不能因 Snackbar 抖动改变输入栏位置。

### 6.5 消息阅读和滚动

1. 默认用户消息与助手消息层级清楚，正文最大宽度和气泡边距符合现有视觉规范。
2. 流式生成时，用户处于底部附近才自动跟随；用户主动上滑后保持阅读位置。
3. 用户离开底部时，出现轻量“回到最新”入口；点击后滚动到底部并恢复跟随。不要在上滑时偷偷拉回。
4. 发送新消息后滚动到新消息；切换分支后定位到对应消息，不无故跳到顶部。
5. Markdown 块、代码、图片、引用和来源区域加载后，避免大幅布局跳动。
6. 长回复有稳定段落行距；不将模型元数据、内部 ID 或调试标签插入正文。

### 6.6 动效与性能

1. 只保留有语义的轻量动效：按压、选中、菜单/弹窗、状态切换。避免大面积模糊、长时间弹跳和连续装饰动画。
2. 常规局部过渡建议控制在约 120–220ms；复杂或低端设备上允许关闭/降级。动画不得阻塞点击和输入。
3. 流式 token 更新要节流/合并 UI 刷新，避免每个 token 都触发全屏高成本重组。
4. LazyColumn 使用稳定 key；附件图片按需解码与加载；离开页面释放 TTS/图片等资源。
5. 不以“动画很流畅”的主观结论代替性能检查；记录明显卡顿场景、设备信息和复现步骤。

## 7. P1：记忆注入边界

现状中 `PromptAssembler` 会将传入的记忆列表合并为一整段 system 消息。长远来看，所有记忆无差别进入每一轮 system prompt，容易使无关偏好或测试指令反复主导回答。

v0.4.0 先做可控的最小方案，不做复杂的向量数据库：

1. 明确区分“用户偏好”“事实”“项目背景”“明确指令”等类别；若数据库暂时无法结构化，先增加来源/类别字段的迁移方案。
2. 旧记忆迁移为普通上下文记忆，不默认提升为强制 system 指令；不得丢失旧数据。
3. 不再默认把前 N 条记忆全部注入每一轮。至少按当前助手和当前问题进行简单相关性筛选，或先由用户明确选择固定记忆范围。
4. 系统提示、助手人设、用户偏好、项目背景和明确指令要在提示词结构中区分，不得把普通事实伪装成高优先级命令。
5. 用户可以查看、编辑、停用和删除记忆；删除后不再进入后续请求。
6. 为记忆注入建立测试：无关记忆不注入；相关记忆可注入；已停用/删除记忆不注入；记忆不能覆盖安全和系统规则。

若完整分类 UI 会显著拖慢核心聊天整改，本轮最低要求是停止无差别注入、保留旧数据，并将完整记忆管理列入 v0.4.1/v0.5.0。

## 8. 视觉实现边界

以现有 `docs/视觉规范.md` 为基线，不重新发明一套 token。

- 保留微信式 A：浅色/深色结构一致。
- 品牌色仅用于选中态、主按钮、链接和少量重点状态；避免全屏图标都用主色。
- 统一图标来源与视觉尺寸；不要混用风格差异过大的图标。
- 页面左右留白、分组间距、列表行、消息气泡、输入栏、圆角和分割线遵循视觉规范。
- 字号跟随系统；正文不低于 14–16sp 的舒适阅读范围，辅助信息可更小但不能承担关键提示。
- 主要文字对比度遵循 WCAG AA 目标：正文至少 4.5:1，大号文字至少 3:1。
- 不新增液态玻璃、彩色渐变、复杂背景或第三套主题。

### 建议保留的视觉基线

- 微信式页面左右边距约 16dp；
- 顶栏与底部导航约 56dp，不含系统安全区；
- 常用点击热区至少 48dp；
- 助手列表头像约 48dp；
- 消息气泡宽度、正文行距和段落间距按视觉规范；
- 列表分割线轻量、缩进一致；
- 浅色/深色使用同一语义 token，不做各页单独调色。

不要为了“看起来高级”加入更多卡片、描边、阴影或动效。百川需要的是统一、有节制、响应直接。
