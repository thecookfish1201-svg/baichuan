# 阶段二问题评审 · 温度、推理深度与 DeepSeek 风格

- 评审：哦鲸鲸（计划与方案协作）
- 日期：2026-11-07
- 对象：阶段二验收反馈三条（温度不生效、思考深度没体现、DeepSeek 风格不像官方 APP）
- 依据：DeepSeek 官方 API 文档、当前仓库代码
- 文档链接：[思考模式](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode/)、[Chat Completions API](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion)、[更新日志](https://api-docs.deepseek.com/zh-cn/updates)、[Temperature 设置](https://api-docs.deepseek.com/zh-cn/quick_start/parameter_settings)

**核对说明**：反馈里"流式解析完全忽略 reasoning_content、消息表只有 content、聊天页没有思考面板"与仓库当前代码不一致。现有代码已经有 `reasoningContent`、`reasoningMs` 两列，`parseStreamChunk()` 已经读取 `delta.reasoning_content`，`ChatScreen` 里已经有折叠的 `ReasoningPanel`，`ChatViewModel` 也会把思考内容落库。所以本文按"代码已有、但用户看到的效果不对"来定位，同时覆盖"发起者安装的是旧 APK"这种可能。开发模型请先做一件事：确认发起者手机上安装的 APK 是否对应包含上述代码的提交，再看后面。

## 一、根因判断

### 1. 温度不生效

**依据一：官方文档明确写了思考模式不支持 temperature。**
DeepSeek 思考模式页面原文："思考模式不支持 `temperature`、`presence_penalty`、`frequency_penalty` 参数。请注意，为了兼容已有软件，设置参数不会报错，但也不会生效。"
Chat Completions 文档的 temperature 条目也补了一句"思考模式下不生效"。

**依据二：思考模式默认是开启的。**
同一页面写明：省略 `thinking` 且不传 `reasoning_effort` 时，默认开启思考模式，强度默认 `high`。

**依据三：现有代码正好落在这个组合里。**
`OpenAiCompatibleAdapter.buildBody()` 无条件写入 `temperature`，`reasoning_effort` 只在非 null 时写入；`AgentEditScreen` 的推理深度选项是 默认/低/中/高，默认值为 null，也就是不传。结果就是：请求体里带着 `temperature=0.7`，思考模式默认开启，服务端照单忽略。

结论：温度不是没传，是传了被模式屏蔽。用户把滑杆从 0.7 拖到 1.5，请求参数变了、模型表现没变，判定"温度没生效"是准确的。同时这也解释了为什么越低或越高的温度都没有体感，因为整段数值区间都不生效。

**次级原因：提示文案把开发侧认知带偏了。**
`AgentEditScreen` 第 261 行写着"DeepSeek 官方 reasoner 模型不支持温度与 reasoning_effort，参数会被服务端忽略；推理链内容仍会正常显示"。这句话里至少两处不准确：官方 OpenAI 格式明确支持 `reasoning_effort`；温度受限的原因是"思考模式"，不是"reasoner 模型"，关闭思考后温度在非思考模式是生效的。按这个错误认知实现，自然不会去做"关闭思考"的入口，温度就永远没有生效机会。

**需要排除的一种可能**：如果用户配置的模型名是 `deepseek-chat` 或 `deepseek-reasoner`，官方更新日志写明这两个名字已于 2026-07-24 停止使用，调用会直接报错，而不是静默无效。请开发模型先确认实际模型名是 `deepseek-flash` 还是 `deepseek-v4-pro`。

### 2. 思考深度没体现

**依据一：档位和官方取值对不上，切换本来就不会有差别。**
官方 OpenAI 格式的 `reasoning_effort` 取值是 `none/low/high/max`，默认 `high`。映射表写明 `medium` 映射为 `high`。现有 UI 给的是 默认/低/中/高：低对应 low，中对应 medium 被服务端当成 high，高也是 high。所以"中"和"高"完全等价，用户切换看不到任何变化是必然结果。另外现有 UI 没有 `max`，也没有 `none`（关闭）。

**依据二：代码里思考链的存储和展示其实已经存在。**
`MessageEntity.reasoningContent`、`reasoningMs`、`OpenAiCompatibleAdapter.parseStreamChunk()` 对 `delta.reasoning_content` 的读取、`ChatViewModel` 的 `onReasoning` 回调与 `finishMessage` 落库、`ChatScreen` 的 `ReasoningPanel`（"已思考（用时 X 秒）"）都在当前代码里。反馈说"完全忽略、没有面板"，只能是三种情况之一：安装的 APK 早于这段代码；模型或中转没有返回 `reasoning_content`；看的是历史消息，旧消息这一列本来就是空。

**依据三：有一个真实缺陷会让"用时"看起来不可信。**
`ChatViewModel` 里 `reasoningMs` 是在整个生成结束时用 `System.currentTimeMillis() - reasoningStart` 计算的，把正文生成的时间也算进去了。思考 3 秒、正文生成 7 秒，面板会显示"已思考（用时 10 秒）"。即使面板显示出来了，用户也会觉得数字不对。正确做法是在首个 `content` 增量到达时冻结思考结束时间。

**附带结论**：官方现在用 `thinking` 和 `reasoning_effort` 控制模式与强度，不再靠模型名区分思考与非思考。"reasoner 模型不支持 reasoning_effort"这个前提已经不成立，相关文案和实现思路都要按新文档改。

### 3. DeepSeek 风格不像官方 APP

**依据一：当前只做了换色，没有做结构。**
`ChatScreen` 里 `deepSeekStyle` 只影响三处：用户气泡改用 surfaceVariant、助手气泡透明、圆角从 10dp 改成 14dp，再加上输入框下方两个 PillButton 和一行免责文案。信息架构还是微信式那套：顶部居中标题加返回、消息只有气泡、操作靠长按菜单。

**依据二：反馈提到的三样，两样是残缺、一样是缺失。**
- 思考面板：有，但是通用样式（文字加箭头、左侧一条竖线），不是官方那种带图标、全宽、有分隔线的折叠条，位置也放在气泡外面。
- 消息操作栏：没有。助手消息下方没有复制、重新生成、更多这一行图标，全靠长按弹菜单。
- 输入框下方按钮：有，但是假的。"深度思考""智能搜索"点击只弹 Toast，没有开关态，也没有和本次请求参数联动。

**依据三：还有几处叠加起来造成"不像"的体感。**
正文没有 Markdown 渲染，代码块、列表、表格都是纯文本平铺；没有模型选择器；没有"新对话"入口；空状态只有一行"开始和 XX 聊天吧"；思考中没有进行态指示。官方 APP 的聊天页是一个完整的信息结构，不是气泡样式。只改颜色，怎么调都不像。

## 二、修改方案

### 2.1 数据层

`messages` 表保留现有两列，补两列：

| 字段 | 类型 | 用途 |
|---|---|---|
| `reasoningTokens` | `INTEGER NULL` | 来自 `usage.completion_tokens_details.reasoning_tokens`，用于验证档位差异和费用统计 |
| `requestParamsJson` | `TEXT NULL` | 记录本次实际发出的 `temperature`、`thinking`、`reasoning_effort`、`top_p`，用于验收和排障 |

`reasoningMs` 的语义改为"思考阶段耗时"，不再包含正文生成时间。

`agents.generationJson` 的结构调整：

```json
{"temperature":0.7,"stream":true,"reasoning":"auto"}
```

`reasoning` 取值改为 `auto/off/low/high/max`，去掉 `medium`。存量数据迁移规则：`medium` 一律写成 `high`，其余原样保留。`auto` 表示不传参数、跟随服务端默认（DeepSeek 默认开启思考且 effort 为 high），这一点要在设置页写清楚，否则用户会以为 auto 是关闭。

`models.capabilitiesJson` 补充能力标记，供 UI 判断哪些参数可以展示：

```json
{"thinking":true,"thinkingEfforts":["low","high","max"],"temperatureInThinking":false,"returnsReasoning":true}
```

数据库版本 `1 → 2`。这是工程第一次迁移，建议同时把迁移测试和 `exportSchema` 补上，否则后面每张表都会欠账。

`ChatMessage` 增加一个字段，为工具调用阶段预留：

```kotlin
data class ChatMessage(
    val role: String,
    val content: String,
    val images: List<String> = emptyList(),
    val reasoningContent: String? = null,
)
```

### 2.2 适配层

新增枚举，替代现在的字符串：

```kotlin
enum class ReasoningEffort { AUTO, OFF, LOW, HIGH, MAX }
```

映射函数放在适配层，不要让 UI 直接拼字符串：

```kotlin
fun ReasoningEffort.toDeepSeekEffort(): String?  // OFF→"none", LOW→"low", HIGH→"high", MAX→"max", AUTO→null
fun ReasoningEffort.toOpenAiEffort(): String?    // OFF→null, LOW→"low", HIGH→"high", MAX→"high"
```

`ModelAdapter` 增加能力声明，或由 `OpenAiCompatibleAdapter` 内部按协议与模型名判断：

```kotlin
data class ModelCapabilities(
    val supportsThinking: Boolean,
    val thinkingEfforts: List<String>,
    val temperatureInThinking: Boolean,
    val returnsReasoning: Boolean,
)
```

`buildBody()` 的规则改成：

- `OFF`：写 `thinking: {"type":"disabled"}`，不写 `reasoning_effort`。此时才写 `temperature`。
- `LOW/HIGH/MAX`：写 `reasoning_effort`，可选同时写 `thinking: {"type":"enabled"}` 明确语义（`thinking` 优先于 `reasoning_effort`，两个都写不会冲突）。此时**不写** `temperature`，避免制造"传了但被忽略"的假象。
- `AUTO`：两个都不写，跟随服务端默认。
- 不给 DeepSeek 发 `top_p`：`deepseek-flash` 非思考模式恒为 1.0，思考模式只接受 0.95–1.0，暴露出去只会增加误解。其他供应商按能力标记决定。

流式解析补三件事：

- 记录首个 `reasoning_content` 与首个 `content` 的时间点，返回给状态层计算思考耗时；
- 读取 `usage.completion_tokens_details.reasoning_tokens` 和 `prompt_tokens_details.cached_tokens`；
- 解析失败时保留已有内容，不要整段丢弃（现有 `try/catch` 返回空已经是这个行为，保持）。

多轮回传规则写进适配器，现在就要留好口子：

```kotlin
data class ChatRequest(
    val model: String,
    val messages: List<ChatMessage>,
    val temperature: Double = 0.7,
    val stream: Boolean = true,
    val topP: Double? = null,
    val maxTokens: Int? = null,
    val reasoningEffort: ReasoningEffort = ReasoningEffort.AUTO,
    val tools: List<ToolDefinition>? = null,
)
```

`buildBody()` 里：请求带 `tools` 时，assistant 消息必须回传 `reasoning_content`，否则 DeepSeek 会返回 400；不带 `tools` 时不回传，传了也会被忽略，白白增加 token。

### 2.3 状态层（ChatViewModel）

`GenerationParams.reasoning` 改为 `ReasoningEffort`，`parseGeneration()` 兼容旧字符串：

```kotlin
private fun parseGeneration(agent: AgentEntity): GenerationParams
// "medium" 读成 HIGH；未知值读成 AUTO；缺失读成 AUTO
```

`ChatUiState` 增加两个字段：

```kotlin
val effectiveParams: EffectiveParams? = null,   // 温度、档位、温度是否生效
val paramNotice: String? = null,                // 例如"当前模型处于思考模式，温度不生效"
```

`generate()` 里做一次有效性判断：`effort != OFF` 且模型 `temperatureInThinking=false` 时，设置 `paramNotice`，UI 把温度滑杆置灰。不要再出现"滑杆能动、参数发了、结果没变"的情况。

思考耗时改为"首个正文增量到达时冻结"：

```kotlin
var reasoningStartAt = 0L
var reasoningEndAt = 0L
// onReasoning 首次：reasoningStartAt = now
// onDelta 首次：reasoningEndAt = now
// reasoningMs = reasoningEndAt - reasoningStartAt
```

`finishMessage()` 扩展一个参数，把本次请求快照写进 `requestParamsJson`：

```kotlin
suspend fun finishMessage(
    messageId: Long,
    status: String,
    content: String,
    error: String? = null,
    reasoning: String? = null,
    reasoningMs: Long? = null,
    requestParamsJson: String? = null,
)
```

会话级开关如果需要（见第三节第 6 条），加一个不落库的会话覆盖：

```kotlin
fun setSessionReasoning(effort: ReasoningEffort)
```

### 2.4 UI

**思考面板**。`ReasoningPanel` 重做，不再只是文字加箭头：

- 折叠条全宽，左侧图标用 Material Symbols 里的思考类图标，不用 Emoji；
- 文案：思考中显示"深度思考中"，结束后显示"已深度思考（用时 X 秒）"；
- 展开区用 `bodySmall`、`onSurfaceVariant`、行高 20sp，超过 240dp 时内部滚动；
- 位置：微信式放气泡上方，DeepSeek 式放气泡内顶部；
- 流式阶段显示进行态指示，正文开始后切回用时文案。

**消息操作栏**。新增 `MessageActions` 组件，助手消息下方一行图标：复制、重新生成、更多（更多里放删除与分支切换）。用户消息保留长按菜单并补"复制"。复制走 `ClipboardManager`，不弹 Toast 也算完成（也可以轻提示）。

**输入框工具条**（DeepSeek 式）：

- "深度思考"改成开关，选中态高亮，点击在 `OFF` 与 `HIGH` 之间切换，并写入会话级参数；
- "智能搜索"阶段三才接，第一版先隐藏，别用 Toast 占位冒充功能；
- 增加模型选择器（顶部栏副标题或输入框上方 chip）；
- 顶部栏右侧加"新对话"入口。

**正文渲染**。引入轻量 Markdown 渲染，至少支持代码块、粗体、列表、引用、行内代码。注意当前构建内存只有约 2.5 GB，优先自写轻量解析或选小体积库，不要引入大型渲染引擎。思考内容保持纯文本，不做渲染。

**空状态**。DeepSeek 式用 logo 加"有什么可以帮您"，配 2 到 3 个建议问题；微信式保持现在的简洁文案但补一个配置入口。

**整体间距**。助手消息 12dp 左内边距、14sp 行距、段落间距 8dp，用户气泡最大宽度不超过屏宽 78%。这些是对齐官方观感最省力的部分。

### 2.5 验收用例

| 用例 | 步骤 | 通过标准 |
|---|---|---|
| 温度生效 | 关闭深度思考，temperature 分别设 0 和 1.5，各请求 3 次 | 请求体包含 temperature 且不包含 thinking；输出差异明显 |
| 温度受限提示 | 开启深度思考 | 温度滑杆置灰，页面出现"温度不生效"提示 |
| 档位差异 | 同一问题分别用 低/高/最大 | `reasoning_tokens` 递增，面板用时递增 |
| 思考面板 | 流式请求 | 先显示"深度思考中"，正文开始后显示"已深度思考（用时 X 秒）"，点击可展开 |
| 操作栏 | 点击复制与重新生成 | 复制内容进剪贴板；重新生成产生新分支，分支计数变化 |
| 工具调用回传 | 构造带 tools 的多轮请求 | 历史 reasoning_content 被回传，服务端不返回 400 |
| 历史兼容 | 迁移数据库后打开旧会话 | 旧消息无思考内容时不显示面板，不崩溃 |
| 风格对照 | DeepSeek 式与官方 APP 并排 | 思考面板、操作栏、输入框工具条位置与交互一致；微信式不回归 |

## 三、需要发起者注意的限制

1. **思考模式与温度互斥**。DeepSeek 官方明确思考模式不支持 `temperature`，这是服务端设计，不是百川的 bug。产品上只有两个选择：开思考时接受温度无效并明确提示，或者提供"关闭思考"开关让温度生效。不能同时宣称两者都可用。
2. **官方模型名已经换了**。`deepseek-chat` 与 `deepseek-reasoner` 于 2026-07-24 停止使用，现在是 `deepseek-flash` 与 `deepseek-v4-pro`，思考模式由参数控制。用户如果按旧教程填了旧模型名，会直接调用失败。建议在服务商模板里内置新模型名，旧名做提示。
3. **推理深度不是通用能力**。官方取值是 `none/low/high/max`，OpenAI 是 `minimal/low/medium/high`，第三方中转可能完全不认。第一版建议只对 DeepSeek 官方做完整映射，其他供应商标注"部分支持"，未知供应商不发送该参数。
4. **思考链能不能显示取决于供应商**。只有返回 `reasoning_content`（或 `reasoning`）才能展示。第三方中转剥离字段很常见，这种情况下不能伪造"已思考"，应如实不显示。
5. **回传规则有坑**。不带 `tools` 时 `reasoning_content` 无需回传；一旦带 `tools`，历史轮次的 `reasoning_content` 必须完整回传，否则 400。阶段五接 MCP、阶段六接 Agent 工具调用之前，这条必须先实现。
6. **深度思考开关的层级需要发起者定**。现在是智能体级配置，官方 APP 是会话级或单次开关。建议做成"智能体给默认值、会话可覆盖"，但这属于产品决策，需要确认后再实现。
7. **成本与延迟**。思考模式输出 token 明显更多，`max` 档更贵也更慢。建议在设置页标注，并在消息上显示思考 token 数，让用户有感知。
8. **第三方中转行为不可控**。可能改写参数、吞掉思考字段、返回 200 但缺 `choices`。验收时必须区分官方接口与中转，不要用中转的结果判定官方适配是否正确。
9. **视觉还原需要设计资源**。官方 APP 的图标、间距、动效是具体的设计产物，逐项对照需要图标素材和截图基准。第一版可用 Material Symbols 近似，但不能用 Emoji 代替，也不能只靠调色号宣称"已还原"。
10. **Markdown 渲染有构建成本**。当前机器构建内存约 2.5 GB，引入渲染库要评估编译时间和包体，优先小体积方案，必要时先只支持代码块与粗体。
